# 06 시스템 아키텍처

- 상태: 뼈대 + 초안 연결 (2026-10-31)
- 이 문서의 목적: V2를 이루는 **코드 모듈, Adapter, 저장, 배포 구조**와 오류 처리, 확장 방향을 정해요.
- 책임 범위: 전체 구성도, 프론트엔드 구조, 수집 모듈, Adapter 인터페이스, 저장 구조, API 연결 방식, 오류 처리, 배포, 확장성, V1과의 분리.
- 다루지 않는 것: 데이터 형식·검증 규칙 → [05](05-data-architecture.md), 공급자 비용·라이선스 → [07](07-data-providers.md), 키 관리·모니터링 절차 → [09](09-operations-security.md)
- 초안: [기초 분석서](01-architecture-design.md) 2장(V1 구조), 4장(권장 아키텍처), 5장(디렉터리), 6-1·6-4절(Adapter 인터페이스·처리 흐름)을 이어받아요.

## 핵심 질문

1. V1과 V2가 같은 저장소에서 서로 영향을 주지 않으려면?
2. 공급자 하나가 바뀔 때 고치는 파일이 Adapter 하나로 끝나는가?
3. 정적 사이트로 시작해서 서버·DB로 옮길 때 무엇을 버리지 않아도 되나?

## 목차

### 1. 전체 시스템 구성
- 초안 [기초 분석서 4-2절]: Adapter → 정규화 → 검증 → 메타·라이선스 필터 → 정규화 저장소 → 공개 빌드 → 정적 웹앱
- 쓸 내용: 구성도 확정, 계층별 책임표(기초 분석서 4-3절)

### 2. 프론트엔드
- 지금 아는 것 [사실]: V1은 `site/app.js` 한 파일 6,639줄, 함수 319개, 전역 상태, `innerHTML` 전체 다시 그리기
- 쓸 내용 [제안]: V2는 `v2/web/`에 페이지·컴포넌트 단위 JS 모듈(빌드 도구 없이 ES 모듈로 시작할지 결정), V1에서 이식할 것(검색, SVG 차트, 디자인 토큰, `sw.js` 캐시 전략)
- 결정 필요: 프레임워크 사용 여부 (불필요한 복잡성 피하기 원칙)

### 3. 데이터 수집 모듈
- 쓸 내용: `v2/pipelines/` 실행 단위(영역별), 일정은 GitHub Actions(`.github/workflows/v2-*.yml`, V1 워크플로와 분리)
- 지금 아는 것 [사실]: V1은 루트 파이썬 36개가 공급자 호출·계산·발송을 섞어 가짐 (기초 분석서 2-3절), 텔레그램 발송이 `realtime_monitor.py`에 묶임

### 4. Adapter
- 초안 [기초 분석서 6-1절]: `fetch_raw` / `normalize` / `health`, `registry.yaml`(영역 × 시장 → Adapter, 라이선스 상태)
- 쓸 내용: 공통 재시도·한도·원본 저장(`adapters/base.py`), V1 호환 층(공통 레코드 → yfinance 모양)은 V1 이전용으로만

### 5. 저장 구조
- 쓸 내용: 원본(비공개) / 정규화 / 공개 빌드의 실제 위치
- 초안 [제안]: 처음엔 Actions 아티팩트·캐시, **git 커밋 안 함**. 나중엔 비공개 저장소 또는 객체 저장소. 정규화는 "파일 하나 = 엔터티 하나"로 DB 테이블과 맞춤
- 결정 필요: 저장소 방침 [Q-02]

### 6. API 연결
- 쓸 내용: 공급자 호출은 수집 단계(서버 쪽, Actions)에서만, 브라우저에서 공급자 직접 호출 금지(키 노출) — 예외: 사용자 자기 키 방식 [Q-06]

### 7. 오류 처리
- 초안 [기초 분석서 6-2·6-4절]: 429/5xx 재시도 3회(2·4·8초), 4xx 즉시 실패, 실패 시 지난 정상본 + `stale`, 검증 경고는 `check`
- 쓸 내용: 오류 종류별 처리표, 사용자 화면 문구(03)와 운영 알림(09) 연결

### 8. 배포 구조
- 지금 아는 것 [사실]: V1 `pages.yml`이 `main` 기준으로 GitHub Pages 배포, 한 저장소 = Pages 사이트 하나 [추정, 확인 필요]
- 쓸 내용: V2 미리보기(아티팩트+캡처) → 운영 배포 경로. GitHub Pages는 상업 SaaS 금지라 상업 오픈 전 이전
- 결정 필요: [Q-03] 호스팅, [Q-11] 코드 위치

### 9. 향후 확장성
- 쓸 내용: 서버·DB 도입 조건(사용자 데이터 동기화, 호출량, 라이선스가 서버 측 표시만 허용할 때), 그때 `build/`가 API 응답 생성기로 바뀌는 구조
- 하지 않을 것: 처음부터 서버·DB·로그인

### 10. V1과의 분리
- 초안 [기초 분석서 5장]: `v2/` 디렉터리, V2 워크플로는 `develop-v2`에서만, `paper/`·`site/` 안 건드림, Secrets `V2_` 접두어 [Q-12]
